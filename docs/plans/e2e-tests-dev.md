# Plan: End-to-end tests against dev after deploy

Card: "End-to-end tests against dev after deploy" (https://trello.com/c/BfS3HYkC/25-end-to-end-tests-against-dev-after-deploy)
Branch: `feature/e2e-tests-dev` (based on `origin/development`). All paths are relative to the repo root.

## Goal
Add Playwright (TypeScript) tests in `e2e/` and a new workflow `e2e.yml`. After "Update deploy manifests" succeeds for `development`, the workflow waits until the dev backend reports the deployed commit through `/api/actuator/info`, then runs a smoke test and a create/report/cleanup scenario against `E2E_BASE_URL`. To make that wait possible, the backend jar gets a `git.properties` file (Gradle git-properties plugin, fed with the checkout's `.git` in the image build), and nginx exposes exactly `/api/actuator/health` and `/api/actuator/info`. The run is informational only: it gates nothing.

## Changes

### What was checked
- **How the workflows chain.** `build-images.yml` runs on push to `development`/`main`.
  - It checks out `GITHUB_SHA`, the pushed commit, at the default ref.
  - It tags images with `type=sha,format=short`, i.e. `GITHUB_SHA[:7]`.
  - `update-deploy.yml` ("Update deploy manifests") runs on `workflow_run` of "Build images" and writes `github.event.workflow_run.head_sha[:7]` as the dev tag.
  - So the image tag, the commit the image is built from, and `head_sha` are the same commit.
  - In `e2e.yml`, `github.event.workflow_run` is the "Update deploy manifests" run. GitHub gives that run the `head_branch` and `head_sha` of the "Build images" run that triggered it, which is the pushed commit.
  - **The workflow waits for `github.event.workflow_run.head_sha`.** It is confirmed on the first real run (Risk R1).
- **The backend image has no `.git`.** `build-images.yml` uses `context: backend`, `backend/Dockerfile` copies only `gradlew`, the build files, `gradle/` and `src/`, and `.git` sits at the repo root, outside the context. The plugin therefore cannot find a repository during `docker build` today. The fix is a named build context, described under `backend/Dockerfile` below.
- **Actuator exposure.** `application.properties` already has `management.endpoints.web.exposure.include=health,info,prometheus`, and `PrometheusEndpointIT.exposesOnlyHealthInfoAndPrometheusOverHttp` checks it. Spring Boot's `GitInfoContributor` is on by default and becomes active as soon as `classpath:git.properties` exists. In the default "simple" mode it renders `git.commit.id` as the short id (7 characters). **No `application.properties` change is needed**, and no new endpoint is exposed.
- **nginx.** `location /api/` proxies to `http://backend:8080` without a URI, so `/api/actuator/x` reaches the backend as `/api/actuator/x`, which returns 404 (there is no such mapping). The Ingress sends everything to the frontend (`infra/helm/pet-project/templates/ingress.yaml`). Exact-match (`=`) locations take priority over prefix locations and match only their own URI.
- **Path-parameter traversal (pre-existing, open).**
  - nginx matches locations on the normalised URI, but without a URI in `proxy_pass` it forwards the raw one.
  - `..;` is not a dot segment for nginx, so `/api/..;/actuator/prometheus` matches `/api/` and reaches Tomcat unchanged.
  - Tomcat removes `;` path parameters before it resolves `..`. `rejectSuspiciousURIs` is off by default, and there is no Spring Security firewall.
  - Whether the request then reaches the actuator depends on how Spring MVC resolves its lookup path (the raw request URI, which is not dot-normalised, or the normalised servlet path). This is not known without a test.
  - The Step 0 probe (Tests) establishes it, and Q7 decides what the plan does about it.
  - Every other traversal form (`/api/../`, `%2e%2e`, `%2F`) is normalised by nginx before the location match and ends up outside `/api/`.
- **Dependency locking.** `lockAllConfigurations()` does not cover the buildscript/plugin classpath (ADR 0007, Consequences: "The Gradle plugin (buildscript) classpath is neither locked nor scanned"). So the plugin is expected to leave `backend/gradle.lockfile` unchanged. The implementer still runs `./gradlew dependencies --write-locks` and commits any diff, as `CLAUDE.md` requires.
- **Data limits.**
  - `category.name` is `varchar(64)`, unique case-insensitive including archived rows, and `@NotBlank @Size(max = 64)`.
  - `expense.note` is at most 255 characters.
  - `GET /api/expenses` accepts any `from <= to` and `categoryIds`.
  - The report includes archived categories only if they have expenses or a limit in the month.
- **UI hooks** that the tests use (accessible names already in the code):
  - nav buttons "Expenses", "Month" and "Categories";
  - forms "New category" and "New expense" (`aria-labelledby` headings);
  - labels "Name", "Amount", "Category", "Note";
  - buttons "Add category", "Add expense", "Delete" (a `window.confirm` dialog) and "Archive";
  - status texts "Category added.", "Expense added.", "Expense deleted." and `Category "<name>" archived.`;
  - tables "Categories", "Expenses this month" and `Report for YYYY-MM`.
- **e2e stays out of the existing test commands.** Vitest, `tsc -b` and oxlint run with `frontend/` as root, and Gradle only sees `backend/`. The repo root has no `package.json`. Neither `./gradlew test` nor `npm test` picks up `e2e/`.

### Run id and names (D4, D5, AC10)
- `E2E_RUN_ID`:
  - CI sets `gh-<github.run_id>-<github.run_attempt>`.
  - Locally the default is `local-<Date.now() in base36>-<4 random hex>`.
  - It must match `^[a-z0-9-]{1,32}$`, otherwise the config throws.
  - `playwright.config.ts` assigns it with `process.env.E2E_RUN_ID ??= …` in the main process, so every worker inherits the same id.
- **Per-test name:** `e2e-<runId>-<6 random hex>`, with the hex from `node:crypto`. A fresh nonce per test attempt means a local re-run with the same `E2E_RUN_ID` cannot hit the 409 "duplicate name" error.
  - Maximum length is 4 + 32 + 1 + 6 = 43 characters, within the 64 limit. The helper asserts `length <= 64` and the `e2e-` prefix.
  - In CI the length is about 30 characters (run id ≤ 20 digits, attempt ≤ 3 digits).
- The same string is the category name and the expense `note` (≤ 255).

    2. Categories tab: "Archive" in the name's row. Expect `Category "<name>" archived.` and the status cell "Archived".

- **The wait logic is split into a module and an entry script,** both run with Node 24's built-in type stripping and with no imports besides `node:` builtins and each other (`.ts` extensions).
  - `e2e/scripts/waitForDeploy.ts` has no side effects. It exports:
    - `parseInputs(env)`, returning `{ ok: true, baseUrl, expectedSha, timeoutMs, intervalMs }` or `{ ok: false, message }`;
    - `matchesCommit(expectedSha, reportedId)`;
    - `describe(result)`, which maps a status/body/error to the observation text and the reported id;
    - `timeoutMessage(...)`;
    - `waitForDeploy(inputs, deps)`, where `deps` is `{ fetchInfo, now, sleep, log }`, returning `Promise<0 | 1>`.
  - `e2e/scripts/wait-for-deploy.ts` is the entry. It calls `parseInputs(process.env)`; on `ok: false` it prints the `::error::` line and sets exit code 2. Otherwise it runs `waitForDeploy` with the real `fetch`, `Date.now`, `setTimeout` and `console.log`, and sets `process.exitCode` to the result.
  - `e2e/scripts/waitForDeploy.test.ts` uses `node:test` and `node:assert/strict`, with a fake clock and a fake fetch. It covers:
    - `matchesCommit`: true for a 7-character and a 40-character prefix of the expected SHA; false for another commit, for a non-hex value and for an id shorter than 7;
    - polls of HTTP 502, then the old commit, then the new commit: returns 0 and logs each change of observation once;
    - never matching: returns 1 after the timeout, and the message contains `::error title=dev is not on the expected commit::`, the short SHA, "10 minutes" and the last observation;
    - `parseInputs`: a missing `E2E_BASE_URL` gives the "create the repository variable" text, and a bad `EXPECTED_SHA` names the variable;
    - the entry script started with `spawnSync(process.execPath, ['scripts/wait-for-deploy.ts'], { env: {} })` exits with status 2.
- Behaviour of `node scripts/wait-for-deploy.ts` (AC3, AC6):
  - Inputs: env `E2E_BASE_URL` (required, http(s), trailing `/` removed), `EXPECTED_SHA` (required, `^[0-9a-f]{40}$`), `WAIT_TIMEOUT_SECONDS` (default 600) and `POLL_INTERVAL_SECONDS` (default 10). Bad input exits 2 with a `::error::` line that names the variable. For a missing `E2E_BASE_URL` it says "create the repository variable E2E_BASE_URL (Settings > Secrets and variables > Actions > Variables)".
  - Loop until the deadline: `fetch(base + '/api/actuator/info', { signal: AbortSignal.timeout(5000), cache: 'no-store' })`.
  - The observation is one of `HTTP <status>`, `no git commit in /actuator/info`, `commit <id>` or `<error message>`. It is logged with the elapsed seconds whenever it changes, and at least once a minute.
  - Success: `git.commit.id` is a string matching `^[0-9a-f]{7,40}$`, and `EXPECTED_SHA.startsWith(id)`. It prints `dev runs <sha7> (after <n>s)` and exits 0.
  - Timeout: exits 1 with
    `::error title=dev is not on the expected commit::<base> did not report commit <sha7> within 10 minutes (last: <observation>). Check that "Update deploy manifests" pushed "deploy(dev): <sha7>" to pet-project-deploy and that Argo CD synced pet-project-dev.`
    The text "10 minutes" is derived from `WAIT_TIMEOUT_SECONDS`.

### `.github/workflows/e2e.yml` (new, AC2, AC3, AC6, AC11–AC13)
Header comment: what it does, ADR 0022, "not a gate", why it runs only for `development`, and that `workflow_run` always runs `main`'s copy of this file (ADR 0004), so it takes effect only once it reaches `main`.

```yaml
name: E2E (dev)
on:
  workflow_run:
    workflows: ["Update deploy manifests"]
    types: [completed]
    branches: [development]
permissions:
  contents: read
concurrency:
  group: e2e-dev
  cancel-in-progress: true   # a newer deploy supersedes the older run (its SHA will never be served)
jobs:
  e2e:
    name: Playwright against dev
    if: >-
      github.event.workflow_run.conclusion == 'success'
      && github.event.workflow_run.head_branch == 'development'
      && github.event.workflow_run.head_repository.full_name == github.repository
    runs-on: [self-hosted, home]
    timeout-minutes: 30
    defaults:
      run:
        working-directory: e2e
```

Steps, in order:
1. `actions/checkout@v6` with:
   - `ref: ${{ github.event.workflow_run.head_sha }}`, so the tests match the deployed code (the default for `workflow_run` would be `main`);
   - `clean: true`, `persist-credentials: false`;
   - `sparse-checkout: e2e`.
   No pre-checkout workspace wipe: this job holds only a `contents: read` token, like the `ci.yml` jobs, and is not a token-bearing workflow in the sense of ADR 0021.
2. "Check E2E_BASE_URL": `env: E2E_BASE_URL: ${{ vars.E2E_BASE_URL }}`. Fails fast with the same `::error::` text if it is empty.
3. "Keep Playwright browsers in RUNNER_TEMP": `echo "PLAYWRIGHT_BROWSERS_PATH=${RUNNER_TEMP}/ms-playwright" >> "$GITHUB_ENV"`. A step is needed because the `runner` context is not available in job-level `env`. `RUNNER_TEMP` is emptied per job, so no browser persists on the host.
4. `actions/setup-node@v6` with `node-version: "24.21.0"` and `package-manager-cache: false` (ADR 0006, ADR 0021).
5. `npm ci`.
6. "Install Chromium (pinned)": `npx playwright install --only-shell chromium`, then `npx playwright --version`. The comment says the version is pinned by `e2e/package-lock.json` (`@playwright/test` 1.63.0), which fixes the Chromium build, and that only Chromium is installed (AC13).
7. "Wait until dev runs this commit": `node scripts/wait-for-deploy.ts`, with env `E2E_BASE_URL` (from `vars`) and `EXPECTED_SHA: ${{ github.event.workflow_run.head_sha }}`. Untrusted values reach the script only through `env:` (ADR 0006). The installs run first so they overlap with Argo CD's sync time, and the 10-minute budget starts at this step.
8. "Run Playwright": `npm run e2e`, with env `E2E_BASE_URL` and `E2E_RUN_ID: gh-${{ github.run_id }}-${{ github.run_attempt }}`.
9. "Upload Playwright report and traces": `if: failure()`, `actions/upload-artifact@v5` with:
   - `name: e2e-playwright-report-attempt-${{ github.run_attempt }}`;
   - `path: e2e/playwright-report` and `e2e/test-results`;
   - `retention-days: 7`;
   - `if-no-files-found: ignore` (a failed wait produces no report).

**Permissions, secrets and fork safety:**
- Only `contents: read`. No secrets.
- `vars.E2E_BASE_URL` is a variable, not a secret.
- `upload-artifact` uses the runtime token and needs no extra permission.
- Fork safety:
  - "Update deploy manifests" runs only after "Build images", which is push-only on `development`/`main`, so forks can never start this chain.
  - The `head_repository` check is a fail-closed extra guard.
  - `pull_request_target` is not used.

### `.github/workflows/ci.yml`: new job `e2e-check` (type-check and unit tests of the wait script)
- **What it runs.** Same `runs-on` expression as every `pull_request` job (ADR 0021) and `timeout-minutes: 10`. Steps:
  1. checkout (`clean: true`, `persist-credentials: false`);
  2. `setup-node` 24.21.0 (`package-manager-cache: false`);
  3. `npm ci` with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD: "1"`;
  4. `npm run typecheck`;
  5. `npm run test:scripts` (`node:test`, fake fetch and clock, no network);
  6. `npx playwright test --list` with `E2E_BASE_URL: http://e2e.invalid`. This loads the config and discovers the tests without a browser or network.
- **Why.** Without this job, a type error or a broken config in `e2e/` would only show up after the merge, as a red post-deploy run. The job costs about a minute, needs no browser and contacts nothing.
- **No lint.** Linting would need oxlint as another devDependency in `e2e/` (open question Q6).
- Update the header comment from "Six independent jobs" to seven, naming the e2e type-check.
- The existing Trivy fs scan (`scan-ref: .`) picks up `e2e/package-lock.json` automatically. Playwright packages are scanned and can fail the gate (ADR 0007).

### `.github/workflows/build-images.yml`
In the "Build image" step:

```yaml
          # backend only: the checkout's .git as named context "gitdir" (replaces the empty stage in
          # backend/Dockerfile), so the jar's git.properties carries this commit (ADR 0022).
          build-contexts: ${{ matrix.service == 'backend' && 'gitdir=.git' || '' }}
          build-args: ${{ matrix.service == 'backend' && 'REQUIRE_GIT_DIR=true' || '' }}
```

- The checkout runs with `persist-credentials: false` after a workspace wipe, so the `.git` holds no token.
- `.git` is only bind-mounted read-only into the `bootJar` step and is never written to a layer, so it does not reach the image or the `type=gha` cache. Its content is still part of that step's cache key, so the jar is rebuilt for every new commit.

### `backend/Dockerfile`
- Add a first stage `FROM scratch AS gitdir`, with a comment: it is empty by default, and `build-images.yml` overrides it with the named context `gitdir`. BuildKit replaces a stage of the same name with a named context.
- `WORKDIR /app` and the final `COPY --from=build /app/build/libs/*.jar app.jar` stay as they are.
- Replace the `bootJar` line with the following. A bind mount is read-only by default. `.git` is never copied into a layer: Gradle reads it through `-PgitDir` (see `build.gradle`). With `REQUIRE_GIT_DIR=true`, a missing context or a plugin that silently generated nothing fails the image build, instead of surfacing later as a 10-minute e2e timeout.
  ```dockerfile
  ARG REQUIRE_GIT_DIR=false
  RUN --mount=type=bind,from=gitdir,target=/tmp/gitdir \
      if [ -f /tmp/gitdir/HEAD ]; then set -- -PgitDir=/tmp/gitdir; \
      elif [ "$REQUIRE_GIT_DIR" = true ]; then echo "build context gitdir (.git) is missing" >&2; exit 1; fi; \
      ./gradlew bootJar --no-daemon "$@" \
      && if [ "$REQUIRE_GIT_DIR" = true ] && [ ! -f build/resources/main/git.properties ]; then \
           echo "git.properties was not generated" >&2; exit 1; fi
  ```
- Do **not** add a `# syntax=` line: BuildKit's built-in frontend supports `RUN --mount`, and a syntax image would be one more unpinned image.
- A local `docker build -t pet-backend backend` keeps working. It produces a jar without `git.properties`.

### `backend/build.gradle`
- `plugins { … id 'com.gorylenko.gradle-git-properties' version '4.0.1' }`

      failOnNoGitDirectory = false   // builds without .git (local docker build, source tarball) still work

### `frontend/nginx.conf` (AC4)
**Only if the Step 0 probe shows Tomcat is affected and the answer to Q7 is A,** add this as the first lines inside the existing `location /api/` block. The proxy lines stay unchanged.

## Risks and open questions

**Open questions (need the user's confirmation):**
- **Q1, new dependencies.** `@playwright/test` 1.63.0, `typescript` ~6.0.2 and `@types/node` ^24.13.3 in `e2e/`, the Gradle plugin `com.gorylenko.gradle-git-properties` 4.0.1, and the Chromium headless shell from Playwright's CDN (see the table above). Please confirm.
- **Q2, deviation from ADR 0006 (accepted).** Chromium on a bare Ubuntu host needs system libraries (libnss3, libgbm1, libasound2t64 and others) that the documented host baseline does not include.
  - The plan **extends the host baseline**: a one-time `sudo npx playwright@1.63.0 install-deps chromium` by the user, repeated after Playwright bumps. It also records that the browser download is pinned by version but not by a workflow SHA-256.
  - ADR 0006 and README "CI runner" are amended. ADR 0021 already says baseline changes go through those two places.
  - The alternative is running the tests in `mcr.microsoft.com/playwright:v1.63.0-noble` pinned by digest. It keeps the host unchanged, but it runs as root (ADR 0021 warns about root-owned files in `_work`) and does not see the host's `/etc/hosts`, so `E2E_BASE_URL` would need `--add-host`/`--network host` handling.
  - Which do you want?
- **Q3, clarification of ADR 0021 (accepted).** `e2e.yml` follows "Update deploy manifests", which is itself a `workflow_run` workflow, not a push workflow. The intent of the rule (no fork code on the runner) holds, because the chain starts at the push-only "Build images". The plan amends the wording explicitly instead of relying on interpretation. Please confirm.
- **Q4, runner reachability.** The runner host must resolve and reach the host in `E2E_BASE_URL` (for `dev.pet.local`, an `/etc/hosts` entry pointing at the k3d ingress). This is a manual host step for you, documented in README.
- **Q5, `ci.yml` `e2e-check`.** Added: type-check plus `playwright test --list` on every PR, with the fork-aware `runs-on`. It adds a seventh serial job on the single runner (about 1 minute). Confirm, or drop it to keep PR CI unchanged.
- **Q6, lint for `e2e/`.** Not added: it would need oxlint as another devDependency in `e2e/`. Add it?
- **Q7, path-parameter traversal `/api/..;/actuator/prometheus` (AC4, AC17).** The Step 0 probe settles whether Tomcat 11.0.26 with Spring MVC is affected. If it is not, nothing changes and the case is only guarded by tests. If it is, choose one:
  - **A (recommended): reject `;` in `/api/` paths in nginx.**
    - What: `if ($uri ~ ";") { return 400; }` inside `location /api/`. It is configuration only, at the edge that creates the exposure, and needs no Java code (ADR 0008).
    - Behaviour change: only API requests with `;` in the path change, from "Tomcat strips the parameter" to 400. The frontend never sends `;`, because `URLSearchParams` encodes it in queries and nothing uses it in paths.
    - Tests: check (b) gives 400, the smoke test on dev asserts 400, and the characterisation probe documents why the rule exists.
  - **B: set Tomcat's `rejectSuspiciousURIs=true`.**
    - What: a Spring Boot `server.tomcat.*` property if Boot 4.1 has one, otherwise a `WebServerFactoryCustomizer<TomcatServletWebServerFactory>` bean of about 10 lines in `backend/src/main`.
    - Effect: protects the backend regardless of the proxy. But it is backend code plus a broader behaviour change: every URI the Servlet spec calls suspicious gets 400, also for in-cluster callers.
    - Tests: the safe probe passes and the smoke test asserts a status >= 400.
  - **C: accept the gap in this card and split the fix into a separate card.**
    - AC4 is then delivered except for this pre-existing path, and the gap is recorded in ADR 0022.
    - The smoke test is `test.fixme` with the card link, and the probe stays a characterisation test.
  - The plan does not pick an option until you answer. Without an answer, the implementer stops after Step 0.
- **Q8, failure artifacts in a public repository.** For 7 days any signed-in GitHub user can download the HTML report, traces and screenshots, which show dev data and the dev host name. The plan accepts this, because dev holds no real data, and records it in ADR 0022. Alternatives: a shorter retention, or uploading only the HTML report without traces (the card asks for traces). Confirm the plan's choice?

**Risks:**
- **R1, `head_branch`/`head_sha` in a two-level `workflow_run` chain.**
  - What the plan assumes: GitHub gives the "Update deploy manifests" run the head branch and SHA of the "Build images" run, so `branches: [development]` matches and `head_sha` is the pushed commit.
  - How it is verified: on the first real run.
  - If the assumption is wrong, `e2e.yml` would never trigger, or would wait for the wrong SHA and time out with the clear message.
  - Fallback: trigger on "Build images" instead. The wait absorbs the extra minute of "Update deploy manifests".
  - The chain depth (Build images → Update deploy → E2E) is within GitHub's limit.
- **R2, first activation.** `workflow_run` runs `main`'s copy of `e2e.yml`, so nothing runs until the change is promoted to `main`. Later edits to `e2e.yml` also take effect only on `main`, while the tests themselves come from the deployed `development` commit.
- **R3, Docker named-context mechanics.** These are verified locally by check (a). If one of them fails, the implementer reports back instead of improvising.
  - an empty `scratch` stage bind mount;
  - BuildKit overriding a stage with a named context;
  - JGit reading a shallow, detached clone from a read-only mount without writing to it (if it needs to write, the fallback is to copy it to a writable temp directory inside the same `RUN`, still not persisted to a layer);
  - the plugin 4.0.1 API on Gradle 9.7.1, including an absolute `-PgitDir`.
- **R4, cost.** The backend jar is rebuilt on every push, including frontend-only pushes (about 1–2 minutes), because `.git` changes. Chromium (about 100 MB) is downloaded on every e2e run, because the browser path is in `RUNNER_TEMP`.
- **R5, frontend not version-checked.** Only the backend SHA is awaited. Argo CD rolls out both tags from the same deploy commit, but a short window with an old frontend pod is possible. A frontend version endpoint is out of scope.
- **R6, leftover data.** Cancelled or interrupted runs (`cancel-in-progress`, job timeout) skip fixture teardown and leave an active `e2e-` category with its expense. Names never collide, and the README SQL cleans them up (D4).
- **R7, time zone.** The tests pin `Europe/Warsaw`, the default `APP_TIME_ZONE`. If dev ever sets another `APP_TIME_ZONE`, around midnight the pre-filled date could be rejected.
- **R8, public endpoints.** `/api/actuator/health` and `/api/actuator/info` (commit id and time) also become reachable in prod, because it is the same image. The repo is public, so this reveals nothing new.
- **R9, path-parameter traversal (pre-existing).** This is no longer only a risk: it is established by the Step 0 probe and decided by Q7. The remaining risk is that the Playwright or curl client normalises `..;` and the smoke test or check (b) passes vacuously. Mitigation: `curl --path-as-is`, a one-time look at the request URL in the trace, and the probe uses `HttpClient` with a raw `URI`.
- **R10, devcontainer.** `e2e/node_modules` lands on the macOS bind mount, unlike `frontend/node_modules`, which is a volume. Playwright is pure JS, so it should work. A named volume would be a separate devcontainer change. Local Chromium in the dev container also needs `sudo npx playwright install-deps chromium`.
- **R11, git worktrees.** In a worktree, `../.git` is a file, so the plugin finds no repository directory and the jar has no `git.properties`. `InfoEndpointIT` then fails with a message that points at `-PgitDir=$(git rev-parse --git-dir)`. The comment in `build.gradle` documents this. Regular clones, CI and the Docker build are not affected.
- **R12, single runner occupancy.** Each push to `development` keeps the runner busy for up to 10 minutes of deploy wait plus the tests, which delays the next CI or "Build images" job. This is recorded in ADR 0022 and README "CI runner".

## Out of scope
- Gating prod promotion, rollbacks or any other workflow on the e2e result.
- e2e in PRs or against preview environments, and e2e against prod.
- Browsers other than Chromium, visual regression, accessibility audits.
- A frontend version endpoint, and other backend or frontend behaviour. There are no changes under `frontend/src`, and none under `backend/src/main` or in `application.properties` unless Q7 = B. The only intended behaviour change is the one chosen in Q7.
- Automatic cleanup of `e2e-` data in the dev DB (only the documented manual SQL).
